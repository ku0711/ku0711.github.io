MMO：Go 伺服器與 Unity 客戶端

2026.9 · 個人練習專案 · 兩個 repo

伺服器：權威架構的遊戲後端

以 Go 撰寫，玩家透過單一條 WebSocket 連線登入、進入城鎮並即時戰鬥； server 以固定 tick 推進世界並廣播給所有連線。兩週內以 22 個 vertical slice 逐刀累積， 每一刀都通過 go test -race 才收尾。

Go
Server 權威 單一 tick 扇出 Go WebSocket PostgreSQL / pgx testcontainers race detector

已完成的功能

  • 帳號與連線：登入、角色命名（名字唯一性由資料庫約束保證）、每帳號速率限制
  • 城鎮：點擊移動與朝向同步、公開喊話
  • 戰鬥：ATK／DEF 傷害公式；單體、範圍、連鎖閃電、自我治療四種技能；死亡、復活免疫與自然回復
  • 怪物：屬性與技能由資料表決定；遊走、仇恨追擊與脫戰；生成器依種類配額與重生時間補怪

架構重點

  • 永不信任 client：傷害、冷卻、座標一律在 server 重算，解碼型別只宣告會採信的欄位
  • 單一寫入者：世界狀態由單一 RWMutex 保護，每個可變欄位明定誰能寫，並以靜態 AST 測試守住
  • 出口有界：每條連線一條有界佇列，扇出只由 tick goroutine 非阻塞投遞，塞滿就關連線讓它重連
  • 測試：約 1.2 萬行 production、4.8 萬行測試（684 支），含併發、對抗與負載測試

圖怎麼來的：由 AI 逐項對照程式碼產生 archify 圖檔，節點釘到產圖當時的原始碼行號； 只在架構有結構性變動的那一刀才更新，避免圖與程式脫節。

客戶端：Unity 串接與輸入輔助

Unity 6（URP 2D），自建網路層與 UI 框架，依伺服器的對外協定逐刀串接到連鎖技能； 同時支援桌面滑鼠與手機觸控兩種操作。

Unity · C#
MVVM 依 snapshot_seq 對帳 Unity 6 VContainer R3 UniTask WebSocket

架構

  • 網路層：WebSocket 傳輸、訊息編解碼、接收迴圈切回主執行緒並依型別分派
  • 世界狀態：以 snapshot_seq 重組快照與事件，死亡後的第二則 EnterOk 可重入套用
  • UI 框架：分層 Canvas、DI 組裝、R3 綁定的 MVVM 基底
  • 系統 UI：Loading、訊息堆疊與提示窗；除錯面板不編進正式 build

已完成的功能

  • 基本流程：選角、點擊移動與位置插值、朝向、聊天，斷線與重複登入轉成系統訊息
  • 戰鬥演出：怪物血條、技能施放、傷害數字、連鎖閃電跳躍線、死亡遮罩與復活
  • 輸入輔助：自動鎖定、射程外先走過去再施放、虛擬搖桿、自動戰鬥，全部在 client 完成，伺服器不用改
  • 測試：約 1.9 萬行程式、433 支 EditMode 測試

AI 協作開發流程

Claude Code · 依熟悉程度調整流程

依熟悉程度決定流程多嚴謹

同一個專案的兩端，刻意用了兩種和 AI 協作的方式。判斷依據是：我能不能自己一眼看出 AI 的產出哪裡不對。

流程選擇

伺服器（Go）：不熟 → 嚴謹流程

  • 後端不是我的主場，錯誤不容易當場看出來
  • 拆成七個階段、交給 6 個專責 subagent，每一步產出一份可審查的文件
  • 用固定的驗收門檻與逐項對照補上「看不出來」的部分

客戶端（Unity）：熟悉 → plan mode

  • Unity 是我的本行，架構好不好可以直接判斷
  • 每個功能先在 plan mode 反覆修改實作架構，確認後才讓 AI 動手
  • 省下多階段的文件與 token 成本，把審查集中在架構決策

伺服器：一刀一條分支、每階段一個檔案

每個功能切成一個可以獨立驗收的 vertical slice，依序交給專責的 agent。 agent 每次啟動都是全新的 context，看不到對話歷史，所以階段之間只靠寫進磁碟的文件交接。

流程設計

讓產出可驗證

  • 固定驗收門檻：build、vet、go test -race 三道全過才算完成，不接受「本機跑不出來」
  • 變異驗證：test-writer 刻意把實作改壞、確認測試會變紅，再用檔案備份還原
  • 逐項對照：acceptance 比對規格、架構與風險清單，偏離要逐條列出，沒有偏離也要明講

讓決策可追溯

  • 裁決要有依據：architect 必須指出是哪一條非功能需求逼出這個方案，或明講「沒有需求能區分」
  • 延後要有觸發條件：不做的項目寫進 BACKLOG，附可觀測的重新評估條件，不接受「以後再看」
  • commit 標階段：[spec]、[implement] 等前綴，一眼看出每個 commit 是哪一刀的哪一步

客戶端與跨 repo 協作：文件就是交接

兩個 repo 各自由不同的 AI session 開發，彼此看不到對方的對話，所以銜接完全靠文件。

文件契約

協定是唯一事實來源

  • 伺服器維護對外協定 protocol.md：訊息型別、欄位、close code 與 client 必須實作的規則
  • 伺服器更新協定後，客戶端先把協定文件同步進自己的 repo，再依變更串接；兩邊衝突一律以協定為準
  • 客戶端串接的 commit 標上對應的伺服器 feature 名稱，前後端進度可以直接對照

客戶端的施工文件

  • 目標是讓一個沒有前置脈絡的新 session，照著文件就能接手開發
  • 記錄現況、實作規則與已知問題，只寫 client 怎麼做，不複製協定內容
  • 先寫需求與分工決策再動手：例如自動戰鬥、搖桿等輸入輔助，先評估結論是「全部由 client 處理、伺服器不用改」，採用後就地更新施工文件

伺服器：規則從踩到的問題長出來

伺服器的流程規範寫在 CLAUDE.md 與各 agent 定義裡，不是一次寫好的。每條規則都對應一次實際發生的問題， 並把「為什麼」一起留下，避免之後被看似等價的寫法繞過。

持續修正

未提交的實作被洗掉

test-writer 做變異驗證時用 git 還原檔案，把 implementer 尚未 commit 的整份實作洗回上一版。

每個階段結束就 commit；暫時改動工作區一律用檔案備份，判準是「會不會覆寫工作區」而不是列舉指令名。

AI 反覆替遊戲平衡設限

agent 多次把「怪物比玩家快」「區域擺太近」當成缺陷來擋、來提問，但數值應該由企劃調整。

寫成「機制與資料的分界」：程式只擋會讓程式壞掉的值，玩法關係不擋、不提問，並逐一清掉既有的平衡類檢查。

文件產出了卻沒人讀

architect 連續兩輪把測試規格寫進架構文件，但 test-writer 的必讀清單裡沒有那份檔案。

交接表的「誰必須讀它」必須與每個 agent 的必讀清單一致，改一邊就同步改另一邊。

測試鎖死企劃數值

測試直接比對預設設定裡的技能與怪物數值，企劃每調一次數字，就有一批無關的測試變紅。

測試改用凍結的數值 fixture 自己持有輸入；「規格數字有沒有寫進設定」改由驗收對照，不寫成測試。

伺服器：成本治理，先量測再調整

嚴謹流程的代價是成本：隨著功能累積，每一刀的 token 消耗明顯上升。先寫腳本從 session 紀錄統計各階段用量，找出消耗集中在哪裡，再決定怎麼改。

量測驅動

找出問題

  • 實作階段佔大宗：單一階段約 600 個 turn，context 接近上限，每一輪都重送
  • 常駐文件與規範檔越長越大，每個 agent 每個 turn 都得帶著
  • 切片過大：一刀動到上百個檔案，大量時間花在遷移既有測試

對應調整

  • 切片門檻：預估改動過大時，拆刀必須是選項之一
  • 驗證迴圈要窄：迭代只跑相關測試，完整 -race 留到階段收尾
  • 規範瘦身：例外表、沿革等細節搬到專門文件，常駐規範只留摘要與指向
導入工具前先做 A/B：評估程式碼結構索引工具 CodeGraph 時，以 3 個真實問題、每組各跑 2 次比較， input token −38%、費用 −24%、耗時 −42%，答案品質相當。第一次量測工具完全沒被呼叫，查出是設定與使用指引缺漏， 補齊後重測才採用，並事先寫好退場條件。
